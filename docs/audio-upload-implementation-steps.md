# 实现步骤拆解

本文档记录了实现 PCM 上传 + 播放 + 暂停/恢复的分阶段计划。

## 1) 明确 PCM 协议
- [x] 选定固定格式：采样率、位深、声道数。
- [x] 确定客户端上传接口（例如 `POST /audio`）与内容类型。
- [ ] 确保 I2S 配置与该协议一致。
- [x] 面向音乐播放的建议起点：`44.1kHz / 16-bit / stereo / little-endian PCM`。
- [x] 16-bit = 2 bytes (16 / 8 bits/byte), stereo = 2 channels (L + R) → 每帧 4 bytes。
- [x] 风险提示：持续流式 HTTP 连接可能触发超时或读阻塞问题，需关注长连接稳定性。

## 2) 线程与通道设计
- [ ] 决定是否使用一个数据通道 + 一个控制通道。
- [ ] 现阶段先用 `AtomicBool` 完成暂停/恢复即可，控制通道留作后续扩展（如 stop/seek/flush）。
- [x] 选择 `bounded` 作为数据通道，以限制缓冲增长并形成背压。

## 3) HTTP 接收流水线
- [x] 从 `String` 切换为原始 PCM 字节（`Vec<u8>`）。
- [x] 按块读取请求体，边读边发送。
- [x] 避免一次性读完整个请求体。

## 4) 播放线程
- [x] 在 `main` 中启动独立播放线程。
- [x] 从数据通道消费 PCM 块。
- [x] 暂时仅做“收到就写 I2S”，不处理暂停。

## 5) I2S PCM 输出
- [x] 为 I2S 驱动新增写入原始 PCM 缓冲的方法。
- [ ] 核对缓冲对齐方式与 PCM 格式（按帧还是按字节）。
- [x] PCM 虽然是二进制，但仍有“帧”概念：一帧=所有声道的采样值；写入长度应为帧大小的倍数。

## 6) 暂停/恢复控制
- [ ] 使用 `AtomicBool` 或控制通道进行播放控制。
- [ ] 暂停时不要直接停止写入 I2S，否则可能重放旧 DMA 缓冲导致噪声。
- [ ] 简单方案：暂停时持续写静音帧，恢复时继续写 PCM。
- [ ] 复杂方案：暂停时停掉 I2S/DMA，恢复时重新启动并注意 pop/click。
- [ ] 去抖建议放在 `Button` 抽象层，避免上层重复处理。

## 7) 缓冲水位策略
- [x] 定义高水位和低水位。
- [ ] 高水位用于限制过量缓冲（阻塞接收或丢弃），低水位用于避免欠载（等待或输出静音）。

## 8) 端到端验证
- [x] 从客户端持续发送 PCM 流。
- [ ] 验证播放是否平滑、暂停是否响应及时。
- [ ] 观察内存增长与欠载表现。


```bash
  ffmpeg -i input.mp3 -f s16le -ar 44100 -ac 2 - \
    | http POST http://<esp32_ip>/audio Content-Type:application/octet-stream
```

说明：
  - -f s16le：16-bit little-endian PCM
  - -ar 44100：采样率 44.1kHz
  - -ac 2：双声道
